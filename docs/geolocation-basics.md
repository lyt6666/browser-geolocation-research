# 米级地理定位原理详解

> 本文从零拆解「浏览器如何拿到 1–30 米精度的坐标」，以及整条链路中每个环节的技术细节与坑。

---

## 1. 定位精度从哪来

要理解「米级」，先理解定位精度的来源。现代设备定位是多源融合的结果，按精度从粗到精：

```
IP 归属              → 精度：城市级（数公里）
基站（Cell Tower）   → 精度：数百米（取决于基站密度）
Wi-Fi 热点三角定位   → 精度：几十 ~ 百米
GPS / GNSS 卫星      → 精度：1 ~ 30 米（开阔地带）
```

浏览器本身**不直接控制 GPS 硬件**，它只是通过 Geolocation API 向**操作系统定位服务**发起请求，由系统融合 GPS、Wi-Fi、基站、A-GPS 等多源给出最终坐标 + `accuracy`（精度半径）。

### accuracy 字段的含义

`getCurrentPosition` 返回的 `coordinates.accuracy` 是一个**半径**（米），表示「真实位置有约 95% 概率落在这个半径圆内」，**不是**「误差最多多少米」。

```json
{
  "coords": {
    "latitude": 39.9087,
    "longitude": 116.3975,
    "accuracy": 12.5,        // ← 精度半径 12.5 米
    "altitude": 43.2,        // 高程（米，可能为 null）
    "altitudeAccuracy": null,
    "heading": null,         // 朝向（运动时才有）
    "speed": null            // 速度（运动时才有）
  },
  "timestamp": 1710000000000
}
```

因此「米级定位」的真实含义是：**`accuracy` 小到十米量级**（GPS 良好信号下），而非任何情况下都精确到 1 米。

## 2. 安全上下文：为什么 HTTPS 是前提

浏览器把 `geolocation` 归为 **powerful feature（强大特性）**，与摄像头、麦克风、剪贴板等同级。这类 API 有两条硬规则：

1. **只在安全上下文可用**：HTTPS、或 `localhost`/`127.0.0.1`。纯 HTTP 页面无法调用。
2. **必须用户主动授权**：首次调用弹权限框，用户点「允许」才继续。

对 HTTP 页面的实际表现（现代浏览器）：

| 浏览器 | HTTP 下 geolocation 行为 |
|---|---|
| Chrome/Edge | 直接 `error`，`code=PERMISSION_DENIED(1)` |
| Firefox | 拒绝暴露 API / 立即拒绝 |
| Safari | 同 Chrome，直接拒绝 |

> **推论**：任何想在「非 HTTPS」下拿定位的设计，都必须先解决 TLS。自签证书虽能「过 HTTPS 这个门」，但现代移动端浏览器对自签证书会有额外警告甚至硬拒。这也是防御识别点之一。

## 3. 坐标系：WGS-84 vs GCJ-02 vs BD-09

这是最容易被忽视、也最能体现专业度的一环。

浏览器 Geolocation 返回的经纬度是 **WGS-84**（World Geodetic System 1984），由 GPS 原始信号得出，是国际通用坐标。但中国区地图服务受法规要求，使用加偏后的 **GCJ-02**（俗称「火星坐标」），两者会有 **约 50–500 米**的偏移。

| 坐标系 | 全称 | 使用者 | 与 WGS-84 关系 |
|---|---|---|---|
| WGS-84 | World Geodetic System 1984 | GPS、Google 海外版、浏览器 | 基准（无偏移） |
| GCJ-02 | 国家测绘局 2002 | 高德、腾讯、Google 国内版 | 加偏（非线性偏移，需算法转换） |
| BD-09 | 百度 2009 | 百度地图 | 在 GCJ-02 基础上再偏移一次 |

### 偏移带来的实际问题

- 拿浏览器坐标（WGS-84）直接标到高德地图 → 会**偏到马路对面甚至隔壁街区**（约百米级误差），反而「不精确」。
- 要做「精确到米」的国内地图展示，必须做 **WGS-84 → GCJ-02 转换**。
- 反过来，拿到一个 GCJ-02 坐标要还原真实 WGS-84 位置，也需要逆向偏移算法（近似还原，存在微小残差）。

> ⚠️ 本仓库**不提供**坐标偏移算法的实现代码，只说明原理与存在性，供研究理解。

## 4. 定位请求的完整时序

一次成功的浏览器定位，时序如下：

```
用户打开页面（HTTPS）
      │
      ▼
JS 调用 navigator.geolocation.getCurrentPosition(...)
      │
      ├─→ ① 浏览器检查安全上下文
      │     ├─ 非 HTTPS → 直接 reject（PERMISSION_DENIED）
      │     └─ HTTPS → 进入 ②
      │
      ├─→ ② 浏览器检查权限状态（permission store）
      │     ├─ 已「允许」→ 静默继续
      │     ├─ 已「拒绝」→ 立即 reject
      │     └─ 未决定 → 弹授权框
      │
      ├─→ ③ 用户点「允许」
      │
      ├─→ ④ 浏览器请求系统定位服务（OS 层，非 JS 可控）
      │     └─ OS 融合 GPS + Wi-Fi + 基站 + A-GPS
      │
      ├─→ ⑤ 系统返回 WGS-84 坐标 + accuracy
      │
      ▼
JS 成功回调拿到 { latitude, longitude, accuracy, ... }
```

关键点：**步骤 ④ 发生在操作系统层**，JS 只能「请求」和「读取结果」，无法干预底层定位融合算法。这就是为什么「精度」由设备信号环境决定，而非网页代码能伪造。

## 5. 移动端限制

移动端（iOS Safari / Android Chrome）对定位有额外约束：

1. **自签证书**：iOS/Android 对未受信任的证书链会硬拒或强警告，导致 HTTPS 建立失败 → 定位拿不到。
2. **前台要求**：部分系统要求页面在前台、且用户手势交互后才弹授权。
3. **系统级定位开关**：若用户在系统层面关闭定位，浏览器再努力也拿不到。

这些限制直接决定了「移动端米级定位」的实际成功率远低于桌面端。

---

## 6. 本质总结

米级地理定位的「技术含金量」不在某一处，而在**整条链路**：

- **合规门槛**：安全上下文 + 用户授权（浏览器强制）
- **精度来源**：系统定位服务多源融合（页面不可控）
- **落地门槛**：坐标系的偏移处理（WGS-84/GCJ-02 转换）
- **现实约束**：移动端证书信任与系统开关（成功率瓶颈）

理解这四点，才算真正理解「米级定位」这件事——它既有明确的技术边界，也有清晰的防御切入点。
